# Provider processing locations

Researched 2026-09-07 for [Launch markets and data residency](https://github.com/0xRowdy/true-count/issues/27). The user subsequently accepted the market, publisher and hosting choices in the [canonical resolution](https://github.com/0xRowdy/true-count/issues/27#issuecomment-5573339375). This note preserves the evidence and proposal wording preceding that decision; it is not a contractual residency guarantee. Facts below reflect the official pages checked on that date; configuration and contract qualification remain necessary before production.

The accepted [account lifecycle](../decisions/authentication-account-lifecycle.md), [persistence](../decisions/local-persistence-account-synchronization.md), and [subscription](../decisions/subscription-verification-entitlements.md) designs already select Supabase and RevenueCat and retain separate deletion/operations handoffs. A US primary backend with disclosed provider processing abroad is a supportable **proposal**. “All data stays in the US” is not supported by these providers' ordinary published terms. English language and US storefront availability do not themselves control processing locations.

## Supabase

| Surface | Documented fact and planning implication |
| --- | --- |
| Primary project | Projects have one primary region. Specific US choices are Northern California `us-west-1`, Oregon `us-west-2`, Northern Virginia `us-east-1`, and Ohio `us-east-2`. General region groupings select available infrastructure and are weaker jurisdiction controls. **Proposal:** name one specific US region in deployment configuration after the market decision; `us-east-1` is a viable candidate, not a selection made here. [Regions](https://supabase.com/docs/guides/platform/regions) |
| Authentication | Supabase deploys the Auth server alongside the database and keeps Auth records in its Postgres `auth` schema. Social identity providers and outgoing mail are additional processing paths. [Auth architecture](https://supabase.com/docs/guides/auth/architecture) |
| Storage and exports | Storage's origin is in the project region, but requests pass through a geographically distributed CDN and assets may be cached outside that region. Private buckets enforce authorization; that is distinct from geography. **Prerequisite:** qualify private export delivery, cache behavior, purge and the accepted 24-hour expiry. [Storage CDN](https://supabase.com/docs/guides/storage/cdn/fundamentals) |
| Edge Functions | Default execution follows the caller's nearest supported region. Callers can specify `x-region`, an SDK region, or `forceFunctionRegion` for paths such as webhooks. Explicit regional invocation does not automatically reroute on outage. **Prerequisite:** inventory every invocation path and verify `x-sb-edge-region`; project placement alone does not pin function execution. The documented function list differs from the project list, including no Ohio entry when checked. [Regional invocation](https://supabase.com/docs/guides/functions/regional-invocation) |
| Backups | Pro daily database backups retain seven days; higher plans/PITR have different windows. Database backups exclude Storage object contents. The public backup guide reviewed does not establish exact backup geography. **Prerequisite:** confirm provider backup locations and deletion aging, and separately choose regions/expiry for independent exports and object protection. [Backups](https://supabase.com/docs/guides/platform/backups) |

The August 1, 2026 DPA §6.1 permits processing wherever Supabase/subprocessors maintain facilities. For customer-directed regions it promises storage and primary processing there, with stated service, instruction and legal exceptions. Personnel access is limited by business need, not an express US personnel restriction. This supports a primary-region description, not exclusivity. [Current DPA](https://supabase.com/legal/customer-resources/data-processing-addendum)

The June 1, 2026 subprocessor list includes AWS, Google, Cloudflare, Fly.io and other hosting providers; Supabase Inc. support; and communication, monitoring and security vendors. It lists purposes, **not processing countries**. It does not establish which providers see each True Count data class. Confirm support, control-plane and log processing locations for the purchased services. [Official list](https://supabase.com/legal/customer-resources/subprocessor-list), [dated PDF](https://supabase.com/legal/subprocessor-list/June-1-2026.pdf)

Do not rely on old “all Supabase logs are BigQuery US” assumptions: a July 23, 2026 announcement describes migration of the management log API to ClickHouse. That announcement does not establish the new log storage geography. Treat hosted platform logs, application logs and third-party log drains as separate inventory entries. [Supabase changelog](https://supabase.com/changelog?next=Y3Vyc29yOnYyOpK0MjAyNC0xMC0wMlQwMTowNDo1OFrOAG7eFA%3D%3D&restPage=5)

## PostHog

US Cloud hosting is AWS `us-east-1` in Virginia; EU Cloud is Frankfurt. PostHog permits employee access/impersonation for support and incidents under its documented controls; raising a support ticket is treated as permission to investigate the account unless instructed otherwise. The reviewed handbook supplies no US-only support-access commitment. [Security handbook](https://posthog.com/handbook/company/security)

The June 12, 2026 core subprocessor table distinguishes US Cloud storage from wider processing: AWS, PlanetScale and Modal have US/Germany entries according to selected cloud; Wiz security processing lists Germany and France; Cloudflare transit lists dynamic worldwide edge locations. Therefore US Cloud is not a whole-service US-only guarantee. AI subprocessors are separately conditional on enabling AI features. **Proposal:** enable only the analytics/operational features actually required and qualify additional features before sending them account data. [Subprocessors](https://posthog.com/subprocessors)

Current pricing advertises one-year free and seven-year paid data retention. These are provider plan features, not accepted True Count retention periods; confirm product-specific windows and shorter retention controls for analytics, errors and logs. [Pricing](https://posthog.com/pricing)

Person/event deletion is asynchronous. API deletion needs `delete_events=true`, plus `delete_recordings=true` if recordings exist; deletion status reports pending/completed and a verification timestamp. Avoid reusing a deleted distinct ID, and stop post-deletion ingestion. **Prerequisite:** test completion tracking against the seven-day active-system deletion target, including associated IDs and any separate logs/exports. A queued request is not completion. [Data storage and deletion](https://posthog.com/docs/privacy/data-storage)

The public DPA is a preview: PostHog says the valid countersigned agreement must be generated and signed inside the organization, including on free plans. Capture the actual applicable agreement and subprocessor scope during production setup. [DPA](https://posthog.com/dpa)

## RevenueCat

RevenueCat's published privacy material identifies US AWS data centers for persistent customer storage, while its privacy policy also permits processing in countries where it or service providers operate. This supports US hosting with qualified wider processing, not a customer-selected regional guarantee. The reviewed pages do not document a selectable US subregion or an all-processing US restriction. [Storage statement](https://www.revenuecat.com/privacy), [privacy policy](https://www.revenuecat.com/privacy-policy)

The August 2026 DPA Annex 3 labels ordinary listed subprocessors USA and names infrastructure, logs, analytics, CDN/security and AI vendors. Annex 2 limits staff access by business need. These entries are not enough to establish edge transit or support-personnel geography for the actual integration. §7's end-of-service return/destruction is subject to standard backup/archive practices and requires a request within 30 days after termination; that is not a seven-day end-user deletion SLA. **Prerequisite:** obtain relevant backup/archive aging and support/edge scope, including which optional features activate additional processing. [DPA and subprocessor table](https://www.revenuecat.com/dpa)

Dashboard/API customer deletion removes purchase history and changes reports; it does not cancel Apple or Google subscriptions. **Prerequisite:** verify customer deletion and later deliberate benefit restoration without rebuilding the deleted True Count account, preserving only the accepted minimum purchase-ownership control records. Do not substitute broad provider retention wording for a justified True Count transaction-retention schedule. [Customer deletion](https://www.revenuecat.com/docs/dashboard-and-metrics/customer-profile)

## Connectivity probes: Cloudflare Workers and direct AWS Lambda

The accepted persistence design uses both providers for stateless nonce-echo connectivity probes. Neither calls Supabase; the direct Lambda URL must be in another AWS region from the Supabase project. Probe requests should carry no account identifiers, tokens or private session data. Network metadata, including IP addresses, remains a processing consideration even without an application payload identifying the user.

Workers regional execution requires Regional Services on the configured custom domain; it is distinct from ordinary performance placement. Cloudflare says code and secrets remain globally deployed even when execution is regionalized. Customer Metadata Boundary is a separate control for traffic metadata. The Workers localization guide notes US-region limitations for metrics/analytics; compatibility varies by product and hostname. **Prerequisite if chosen:** qualify the exact plan, custom domain, bypass endpoints, outbound requests, code/secrets, logs and every bound storage service. Do not assume the base Workers price includes those controls. [Workers localization](https://developers.cloudflare.com/data-localization/how-to/workers/), [product compatibility](https://developers.cloudflare.com/data-localization/compatibility/)

Direct AWS Lambda executes across availability zones within the selected AWS region; function URLs have region-specific endpoints. Logs and administrative access need separate processing controls. The exact probe region remains a decision; using another AWS region does not provide independence from AWS as a whole, since Supabase also uses AWS. [Lambda region/AZ model](https://aws.amazon.com/about-aws/whats-new/2026/03/lambda-availability-zone-metadata/), [function URLs](https://docs.aws.amazon.com/lambda/latest/dg/urls-invocation.html)

## Apple, Google and email

Treat Apple/Google identity and store transaction processing separately from Supabase account records and RevenueCat's copy of purchase evidence. Apple permits worldwide transfer/access and says personal data is generally stored in the US. Google operates global servers and permits processing outside the user's country, with independent retention for purposes including financial records. Neither policy makes the app's backend-region setting apply to provider processing. **Prerequisite:** inventory actual sign-in scopes, identity/token fields, store receipts/transaction identifiers, server notifications and provider revocation/deletion paths; distinguish records True Count can erase from records the stores control. [Apple privacy policy](https://www.apple.com/legal/privacy/en-ww/), [Google privacy policy](https://policies.google.com/privacy)

The production email provider remains unselected. Supabase's default SMTP service is limited and intended for testing; production needs suitable custom delivery. Before selecting one, establish hosting, support/subprocessors, delivery-log/message-body retention, recipient/suppression-list deletion, and any Apple private-relay route. SMTP relay delivery and the recipient's mailbox cannot be treated as confined by the database region. [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp)

## Necessary decision and implementation handoffs

1. **[Launch markets and data residency](https://github.com/0xRowdy/true-count/issues/27):** accept the intended launch markets/languages and either a primary-storage commitment with disclosed cross-border processing or a stronger requirement that reopens provider qualification. Name the exact backend region and analytics cloud only after acceptance.
2. **Before production:** keep a data-flow register separating primary records, Auth, exports/Storage/CDN, functions, logs, backups, support, analytics, billing/stores, email and operator access. Record data classes, purposes, regions/countries or documented global scope, provider terms, retention, deletion route and owner. Keep private casino records out of analytics, billing and routine support payloads.
3. **[Backend operating envelope and disaster recovery](https://github.com/0xRowdy/true-count/issues/28):** qualify the identified backup/log/support uncertainties; set finite retention and prove deletion completion and restore suppression across providers. Do not advertise unverified seven-day erasure of every provider backup.
4. **Release disclosures:** align privacy notice and store disclosures with actual enabled SDKs/features and vendor processing. This investigation establishes provider facts; it does not determine jurisdiction-specific legal obligations or authorize launching in any market.
